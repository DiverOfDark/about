Two weeks ago I wrote GitImage, a Kubernetes operator that turns a git URL into a running pod.

You give it a repository:

```yaml
apiVersion: gitimage.dev/v1alpha1
kind: GitImage
metadata: { name: myapp, namespace: team-a }
spec:
  url: git@github.com:you/myapp.git
  ref: main
  secretRef: { name: myapp-git }
```

and put an annotation on a Deployment saying which container runs it. Every commit gets built inside the cluster and rolled out. No external CI, and with S3 storage, no registry at all.

## How it works

- the controller watches the branch, or gets a webhook from GitHub, GitLab or Gitea;
- for every new commit it starts a build Job with BuildKit inside an isolated pod;
- if the commit does not touch the build context, it reuses the last image and skips the build;
- the image goes into any OCI registry or into an S3 bucket;
- an admission webhook replaces the `placeholder` image in the pod with the exact digest;
- a pod created before its image exists waits as `SchedulingGated` and starts as soon as the build is done.

## The fun parts

**Isolation.** Building someone's Dockerfile in your cluster means running someone's code as root. So every build runs in Kata (a separate VM), gVisor, Sysbox or user namespaces. If the chosen mode does not work, the controller refuses to start.

At home this part took the most time 😅 I started with Kata, and builds that wrote big layers kept dying: EIO inside BuildKit, or the whole VM got OOM-killed. Two days later I moved to gVisor. It was faster too: a full crier build took 198 seconds, and the first trackhound build under Kata had taken about 9.5 minutes.

Then I added phos, my photo manager, and gVisor could not build it. `apt` upgrading libssl failed with ENODEV: gVisor's overlay cannot copy up a file that some process has mapped into memory. One workaround crashed the sandbox, another one built phos in 57 minutes.

So twelve days later I went back to Kata, and this time found the real cause. Kata gives the VM 2 GiB plus the pod's memory limit, but the pod's cgroup on the host only got the limit plus 130 MiB. As soon as the page cache inside the VM grew, the host killed the hypervisor. The fix was one number: the RuntimeClass overhead went from 130Mi to 2560Mi. BuildKit's state now lives on a Ceph block volume that stays between builds, so the cache survives too.

**No registry.** In S3 mode the images sit in a bucket (I use Ceph RGW), and every node runs a small read-only OCI server on `localhost:25050`. containerd pulls from localhost over plain HTTP without any node config. So the whole "registry" is a bucket plus a DaemonSet.

**Credentials.** The build never sees the storage credentials. BuildKit pushes to the controller with a token that only works for this one image and dies together with the build Job.

## What is inside

- Rust: controller, admission webhook and node server, 8 crates in total;
- gix for git, BuildKit for the builds;
- a web UI in Svelte: live build logs, workloads and waiting pods, login through OIDC with cluster RBAC;
- a Helm chart and docs on mdBook.

![GitImage UI listing seven images, all Ready: crier, gjallarhorn, about, hugin, phos, trackhound and trmnl-cyberpunk](/img/blog/gitimage-1.jpg)

The e2e tests run on kind with registry and S3 storage, under privileged, gVisor, Kata and Sysbox.

At home it already builds seven of my projects, this blog included. For now it is pre-alpha: two weeks, 81 commits, v0.1.64. It works for me, but I would not put it in production yet 😅
